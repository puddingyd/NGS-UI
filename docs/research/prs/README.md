## 四、後續如何維護？

1. **主流程說明寫「現在實際怎麼做」。** 新方法只在規劃或試算時，寫入計畫／實驗文件；實作與驗證完成後，再更新主流程文件。
2. **每份 review 標記它看的文件與程式 commit。** 外部原稿保留原樣；錯誤、不同意見或補充寫在 response，不回頭替審查者改原文。
3. **response 分清楚「同意問題」「建議方法」「已完成查核」「已實作」。** 本輪選定三項，只表示同意規劃這些工作；尚不代表採用所有 proposed fixes。
4. **驗證文件保存可重現證據。** 記錄問題編號、輸入版本與 hash、程式 commit、工具、比較方式、結果與限制。個體資料及大型工作檔留在適當的院內位置，repo 內保存可分享的彙整與來源索引。
5. **決策有自己的紀錄。** 結案時寫出採用／不採用／待資料，以及理由、證據連結、會影響哪些結果。若改權重、位點、補值、排名或 HR，必須明列新舊版本與相容性；若只改顯示文字，記為呈現調整。
6. **歷史文件不因主文更新而失去對應。** 用固定 commit 保存當時內容，不另複製一整套程式。若回應需實質修訂，新增有日期的修訂版並在本索引標明取代關係；舊版仍可由 Git 追溯。
